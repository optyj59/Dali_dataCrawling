0. 전체 그림 한 슬라이드용 요약

목표

키워드로 유튜브 영상 후보를 많이 모으고

각 영상의 댓글·대댓글을 가능한 한 전부,
그리고 브라우저 없이(request만) 안정적으로 수집하는 것.

구조

search_engine.py
→ 키워드로 검색 결과 페이지의 내부 JSON(ytInitialData + ytcfg) 를 파싱해서
여러 페이지의 videoId 목록을 뽑아냄.

request_engine.py
→ watch?v=VIDEO_ID와,
이어서 호출되는 내부 API youtubei/v1/next 응답 JSON만으로
댓글 + 대댓글을 continuation 토큰이 끝날 때까지 반복 요청해서 모두 수집.

1. 왜 Selenium / Playwright → Requests 방식으로 넘어갔는지

핵심 포인트:
DOM 스크롤 기반은 “보이는 것” 기준이라 느리고, 불안정하고, 매번 결과가 달라졌음.

브라우저 기반에서 겪었던 문제들

스크롤 타이밍·로딩 속도에 따라
한 번은 318개, 한 번은 315개 이런 식으로 계속 들쭉날쭉

답글 버튼(더보기 / 숨기기) DOM 구조가 자주 바뀜
→ 셀렉터 관리가 지옥 + 무한 루프 이슈

헤드리스 모드/일반 모드에서 동작이 달라짐

속도: 몇백 댓글 + 답글에 20분 걸리는 수준

그래서 방향 전환:

“사람 눈에 보이는 DOM”이 아닌
“유튜브 프론트엔드가 실제로 서버와 주고받는 JSON”을 직접 요청해서 파싱하는 쪽으로 전환.

브라우저 없이 requests만으로 동일(혹은 그 이상)의 결과를 얻는 게 목표.

발표할 때 한 줄로 말하면:

“스크롤로 화면을 긁는 대신, 유튜브가 내부적으로 호출하는 JSON API를 직접 따라가서 훨씬 빠르고 안정적인 크롤러로 바꿨습니다.”

2. URL 크롤링 – 검색 결과에서 videoId를 모으는 원리
2-1. 검색 페이지에서 우리가 보는 것 vs 실제 동작

사용자가 브라우저에서 https://www.youtube.com/results?search_query=파이썬+강좌 를 열면,

HTML 안에 그냥 <a href="/watch?v=...">만 있는 게 아니라

ytInitialData 라는 거대한 JSON 덩어리가 <script> 안에 들어있음.

또 하나, ytcfg.set({...}) 라는 설정 JSON도 같이 들어있고,

여기엔 INNERTUBE_CONTEXT, INNERTUBE_API_KEY 등 내부 API 호출에 필요한 정보가 들어있음.

2-2. ytInitialData / ytcfg.set 추출

검색 결과 HTML을 requests.get()으로 가져옴.

문자열에서 직접 위치를 찾음:

tar_init = "var ytInitialData = "
tar_cfg  = "ytcfg.set({"

i_init = html.find(tar_init)
j_init = html.find("};", i_init)
ytinit_str = html[i_init + len(tar_init) : j_init + 1]

i_cfg = html.find(tar_cfg)
j_cfg = html.find(");", i_cfg)
ytcfg_str = html[i_cfg + len(tar_cfg) - 1 : j_cfg]


각각 json.loads() 해서 파이썬 dict로 변환
→ ytinit, ytcfg 두 개 객체 확보.

발표 포인트:

“브라우저를 쓰지 않고도, 검색 페이지 HTML 안에 숨겨져 있는 ytInitialData와 ytcfg.set JSON을 문자열 슬라이싱으로 직접 잘라서 파싱했습니다.”

2-3. videoRenderer에서 videoId 뽑기

ytInitialData 안에는 이런 구조가 계속 반복됨:

{
  "videoRenderer": {
    "videoId": "abc123",
    "title": { "runs": [ { "text": "파이썬 강좌 1" } ] },
    "viewCountText": { "simpleText": "조회수 1.2만회" },
    ...
  }
}


나는 DFS 도는 search_dict() 유틸을 만들어서,
중첩된 dict/list 안에서 "videoRenderer"라는 key를 전부 찾도록 구현.

각 videoRenderer마다:

videoId → "https://www.youtube.com/watch?v={videoId}"

title → 제목

viewCountText → 조회수 텍스트(원하면 숫자로 파싱 가능)

채널명 (longBylineText or ownerText) 도 함께 추출 가능

2-4. continuation을 따라가며 더 많은 결과 긁기

검색 결과 첫 페이지에만 영상이 있는 게 아니고,
맨 아래에 “더보기” 역할을 하는 continuationItemRenderer가 있음.

이 안에 "continuationEndpoint" 가 들어있고,
이게 다음 페이지를 가져오는 내부 API 정보:

"continuationEndpoint": {
  "commandMetadata": {
    "webCommandMetadata": {
      "apiUrl": "/youtubei/v1/search"
    }
  },
  "continuationCommand": {
    "token": "XYZ...."
  }
}


여기서:

apiUrl → "https://www.youtube.com/youtubei/v1/search"

token → 다음 페이지를 요청할 때 필요한 continuation 토큰

요청 방식:

api_url = "https://www.youtube.com" + apiUrl
payload = {
    "context": ytcfg["INNERTUBE_CONTEXT"],
    "continuation": token
}

r = session.post(
    api_url,
    params={"key": ytcfg["INNERTUBE_API_KEY"]},
    json=payload
)
data = r.json()


이 data 안에서도 다시:

videoRenderer 를 DFS로 찾아서 videoId를 모으고

continuationItemRenderer를 찾아서 새로운 토큰을 큐에 추가

토큰이 더 없거나 limit(예: 50개)를 채우면 종료

발표 한 줄 요약:

“검색 페이지에서는 ytInitialData + continuation 토큰을 이용해 youtubei/v1/search를 여러 번 호출하면서 videoId를 안정적으로 많이 모아왔습니다.”

3. 댓글 크롤링 – youtubei/v1/next 기반 전체 댓글 수집 (commentEntityPayload 방식)
3-1. 중요한 깨달음: 첫 댓글 토큰은 ytInitialData 안에 있다

예전 방식이나 다른 영상에서는 `watch?v=` 페이지의 `ytInitialData` 안에 댓글 일부가 포함되기도 했지만, 최신 유튜브 구조에서는 **첫 댓글 페이지를 로드하기 위한 continuation 토큰**이 `ytInitialData` 안에 숨겨져 있습니다.

→ 그래서 request_engine.py의 현재 전략은:

1.  `watch?v=VIDEO_ID` HTML에서 `ytInitialData`와 `ytcfg.set`을 둘 다 뽑아냅니다.
2.  `ytInitialData` 내부를 탐색하여 댓글 섹션의 `continuationItemRenderer`를 찾고, 여기서 **첫 번째 댓글 페이지를 불러올 토큰**을 확보합니다.
3.  이 토큰과 `ytcfg` 정보를 이용해 `youtubei/v1/next`를 직접 POST 요청하여 댓글 JSON을 반복적으로 수집합니다.

3-2. watch 페이지에서 ytInitialData와 ytcfg 추출

검색 페이지 때와 동일하게, `requests.get()`으로 HTML을 가져온 후 정규표현식으로 `ytInitialData`와 `ytcfg.set` JSON 문자열을 추출하고 파싱합니다.

3-3. 최초 댓글 요청: youtubei/v1/next

`ytInitialData`에서 찾은 첫 `token`을 사용해 `next` API를 호출합니다.

요청 방식:
```python
api_url = "https://www.youtube.com/youtubei/v1/next"
payload = {
    "context": ytcfg["INNERTUBE_CONTEXT"],
    "continuation": token  # ytInitialData에서 추출한 토큰
}

r = session.post(
    api_url,
    params={"key": ytcfg["INNERTUBE_API_KEY"]},
    json=payload
)
data = r.json()
```
이 `data` 응답 안에 첫 페이지의 댓글과, 다음 페이지를 위한 새로운 continuation 토큰이 들어있습니다.

3-4. 댓글이 실제로 들어있는 JSON 경로 (entityBatchUpdate)

2025년 기준, 댓글 데이터는 **매우 다른 경로**에 존재합니다.

data 구조 핵심:
```json
{
  "frameworkUpdates": {
    "entityBatchUpdate": {
      "mutations": [
        {
          "payload": {
            "commentEntityPayload": { ... } // 여기에 댓글 하나하나의 정보가 담겨있음
          }
        },
        ...
      ]
    }
  }
}
```

핵심 포인트:

댓글 모델이 `commentViewModel`이나 `commentRenderer`가 아닌, `commentEntityPayload`로 완전히 변경되었습니다.
`frameworkUpdates.entityBatchUpdate.mutations` 배열을 순회하며 각 `payload`에서 `commentEntityPayload`를 뽑아내야 합니다.

파싱은 대략 이런 느낌:
```python
fb = data.get("frameworkUpdates", {}).get("entityBatchUpdate", {})
mutations = fb.get("mutations", [])

for mut in mutations:
    payload = mut.get("payload") or {}
    entity = payload.get("commentEntityPayload")
    if entity:
        comment = self._parse_comment_from_entity(entity, video_id)
        comments.append(comment)

# 다음 페이지용 continuation은 이전과 유사하게
# reloadContinuationItemsCommand 또는 appendContinuationItemsAction 에서 찾음
```

3-5. commentEntityPayload → 우리 표준 댓글 포맷으로 변환

`commentEntityPayload` 구조 예시:
```json
"commentEntityPayload": {
  "properties": {
    "commentId": "Ugw...Ag.9N...I6",
    "content": { "content": "댓글 내용입니다" },
    "publishedTime": "4년 전",
    "replyLevel": 1
  },
  "author": {
    "displayName": "@user-name",
    ...
  },
  "toolbar": {
    "likeCountA11y": "좋아요 123개",
    "replyCountA11y": "답글 5개"
  }
}
```

`_parse_comment_from_entity` 함수의 실제 파싱 로직:
```python
def _parse_comment_from_entity(self, entity, video_id):
    properties = entity.get("properties", {})
    toolbar = entity.get("toolbar", {})
    author_info = entity.get("author", {})

    cid = properties.get("commentId")
    text = properties.get("content", {}).get("content", "")
    author = author_info.get("displayName", "")
    created_time = properties.get("publishedTime", "")
    
    # 접근성 텍스트에서 숫자만 정규식으로 추출
    likes_str = toolbar.get("likeCountA11y", "0")
    likes = self._parse_str_to_int(likes_str)

    reply_count = self._parse_str_to_int(toolbar.get("replyCountA11y", "0"))
    reply_level = properties.get("replyLevel", 0)

    # parent-child 매핑 (commentId에 '.' 포함 여부로 판별)
    parent_id = None
    if cid and "." in cid:
        parent_id, _ = cid.split(".", 1)

    return {
        "id": cid,
        "parent_id": parent_id,
        "video_id": video_id,
        "author": author,
        "content": text,
        "likes": likes,
        "created_time": created_time,
        "reply_count": reply_count,
        "reply_level": reply_level,
        "collection_time": datetime.now()
    }
```

발표할 때 이렇게 설명하면 좋습니다:

“최신 유튜브는 `commentEntityPayload`라는 데이터 모델을 사용합니다. 댓글 내용은 `properties.content.content`에, 작성자는 `author.displayName`에 있고, 특히 좋아요 수는 `toolbar.likeCountA11y` 라는 **웹 접근성용 텍스트**에서 숫자를 파싱해서 가져오는 방식으로 안정성을 높였습니다.”

3-6. continuation으로 끝까지 긁는 루프

이전과 동일한 로직으로, `next` 응답에 포함된 `continuationItemRenderer`의 토큰을 계속 따라가며 더 이상 토큰이 없을 때까지 반복합니다.

5. 정리 – 이 크롤러의 장점 / 한계 / 앞으로 할 수 있는 것
장점

(이전 내용과 거의 동일)
브라우저 불필요 (`requests` 엔진)
DOM 렌더링/스크롤 타이밍 문제 없음
속도 & 자원 효율
유튜브 내부 구조를 이해한 “의미 있는 크롤링”

**추가된 기능: 지능형 필터링**

단순히 댓글만 수집하는 것이 아니라, 수집 가치가 있는 영상을 선별하는 기능을 추가했습니다.

**조회수 필터링:** `requests` 엔진은 댓글을 수집하기 전, `ytInitialData`에서 영상의 조회수를 먼저 확인합니다. 설정된 최소 조회수(`min_views`)에 미치지 못하면 API 요청을 시작조차 하지 않아 불필요한 크롤링을 방지합니다.

**댓글 수 필터링:** 첫 번째 댓글 페이지를 가져온 후, 응답에 포함된 전체 댓글 수를 확인합니다. 이 댓글 수가 최소치(`min_comments`)보다 적으면, 추가적인 페이지 요청을 중단하여 자원을 아낍니다.

한계 / 리스크

(이전 내용과 동일)
내부 JSON 구조 변경 리스크 (`commentEntityPayload`가 또 바뀔 수 있음)
비공식 API 사용으로 인한 차단 가능성
→ `time.sleep`과 같은 적절한 딜레이와 `min_views`, `min_comments` 필터링으로 요청 최소화 필요

6. 발표 때 써먹기 좋은 한 줄 정리 예시

“처음엔 스크롤 기반 Playwright 크롤러로 시작했지만, DOM 구조와 타이밍에 너무 민감해서 유튜브 내부 JSON API를 직접 분석해 `requests` 기반 크롤러로 전환했습니다.”

“검색 단계에서는 `ytInitialData`에서 `continuation` 토큰을 추출해 `youtubei/v1/search`를 반복 호출하며 videoId를 수집했고요.”

“댓글 단계에서는 **`watch` 페이지의 `ytInitialData`에서 첫 댓글 토큰을 확보**한 후, `youtubei/v1/next`를 연쇄적으로 호출했습니다. 응답 데이터의 `frameworkUpdates.entityBatchUpdate.mutations.payload.commentEntityPayload` 라는 복잡한 경로에서 댓글 정보를 안정적으로 파싱했으며, 특히 `likeCountA11y` 같은 접근성 텍스트를 파싱하여 견고함을 더했습니다.”

“또한, 불필요한 수집을 막기 위해 조회수와 댓글 수를 기준으로 영상을 미리 필터링하는 기능도 구현했습니다.”
